# Spike record — storage substrate (2026-08-01)

Backs `DECISIONS.md` ADR-003. Run before ARCHITECTURE was written, because the result changes
the component diagram. The spike code was throwaway and is not in the repo; this is the record.

## Question

Is the single append-only journal viable under the requirements' budgets, or must the design
fall back to a shared event-log substrate with separate materialized stores?

**Pre-committed decision rule** (fixed before running, per the session plan):

- Both performance gates pass at the nominal point → single journal, all else a view.
- Either fails → shared event-log substrate with separate stores. Provenance and replay
  retained; the unification claim dropped.

## Method

Python 3.11 + stdlib `sqlite3` (SQLite 3.45.1, FTS5), NumPy. Process pinned to **1 vCPU** via
affinity; BLAS forced single-threaded. `journal_mode=WAL`, `cache_size=32MB`, `mmap_size=0` (so
memory-mapping does not flatter the numbers), `temp_store=MEMORY`. Durable writer thread
appending at 50/s throughout every retrieval measurement.

**Aged shape is generated statistically, not by simulating consolidation and decay policy.**
Simulating a year of policy would require implementing the hardest logic in the system, in the
wrong language, before ARCHITECTURE existed. Parameters: index churn, supersession chain depth,
page fragmentation (interleaved deletes to induce partially-full pages — `freelist_count`
understates this, so bloat is measured against a `VACUUM INTO` copy), and tombstone fraction.

The live injectable set is held constant while dead rows accumulate around it. Live memories are
100k except in Tier C.

**Retrieval** = four cues + reciprocal-rank fusion: FTS5/BM25, dense top-k, 2-hop recursive CTE
over the entity graph, and a temporal window. It **excludes** query embedding (~15 ms) and
cross-encoder rerank (~50 ms), which are separately budgeted inside §5.7's 300 ms. Storage
therefore gets **≤120 ms**, which is where the gate comes from — it is derived, not arbitrary.

Query terms are drawn from the **mid-frequency band** (ranks 200–5000), where content words
live. The corpus is Zipf-distributed; drawing query terms from the Zipf head would be querying
on stopwords — adversarial rather than representative.

**Two index designs** are contrasted at every point:

- **naive** — one hot index over all rows; the injectable filter is applied after, so the query
  must over-fetch.
- **split** — the hot index contains only injectable rows; no over-fetch, no post-filter.

## Nominal operating point

**Tombstone fraction 0.30, mean supersession chain depth 3.** Declared before the run so the
decision rule stays decidable. **Pre-registered, not derived** — a decision procedure, not a
measured property of any real workload. The curve is the artifact; do not inherit 0.30 as if it
had been measured.

## Tier A/B — tombstone sweep, 100k live constant

| f | total rows | db MB | naive P95 | split P95 | naive over-fetch |
|---|---|---|---|---|---|
| 0.00 | 300,000 | 495 | 106.2 ms | 16.7 ms | 3.0× |
| 0.10 | 311,111 | 508 | 84.3 ms | 15.6 ms | 3.1× |
| 0.20 | 325,000 | 525 | 101.6 ms | 18.1 ms | 3.2× |
| **0.30** | **342,857** | **546** | **94.9 ms** | **16.2 ms** | **3.4×** |
| 0.40 | 366,667 | 575 | 113.9 ms | 18.6 ms | 3.7× |
| 0.60 | 450,000 | 673 | 143.6 ms | 18.7 ms | 4.5× |
| 0.80 | 700,000 | 962 | 258.4 ms | 23.3 ms | 7.0× |

Naive crosses the 120 ms budget at **f ≈ 0.45**. Split is flat, 16.7 → 23.3 ms, across the whole
range. At f = 0.00 the naive design already pays 3.0× over-fetch — with chain depth 3, two
thirds of rows are superseded before the first tombstone exists.

## Other gates at nominal

| Measurement | Result | Gate | |
|---|---|---|---|
| Sustained durable append (`synchronous=FULL`) | 633.2/s | ≥50/s | pass |
| Full index rebuild, replaying fidelity + supersession events | 11.7 s | ≤10 min | pass |
| **Rebuild correctness — exact per-entry fidelity** | **exact match, 0 mismatches** | exact | pass |
| Page bloat vs. `VACUUM INTO` copy | 1.091× | report | — |

**fsync calibration** (so the append number is re-derivable on other hardware): workstation NVMe
p50 **1.14 ms**, p95 **2.12 ms**. VPS shared storage is typically 5–20× slower, putting the same
workload at ~175/s to ~44/s. **The append number does not travel without this caveat.** Group
commit is the mitigation and is a design requirement, not a contingency.

### On the rebuild-correctness assertion

This assertion caught a real fixture bug during development: an earlier version assigned
fidelity to superseded rows without journaling it, so replay could not reproduce current state.
That is exactly the class of error the assertion exists to catch — a rebuild that silently
restores forgotten memories. It is cheap to verify here and expensive to discover later.

## Tier C — live-set scaling

Tier B held the live set constant and grew only the dead set, so it never asked whether the
design holds when the *injectable* set itself is large. Split design only; naive had already
failed. Journal built at 1 event/memory and the all-rows FTS omitted, both stated because
neither is on the split retrieval path and therefore neither can affect the measured latency.

| live set | total rows | db MB | vec MB (f32) | P50 | P95 | P99 |
|---|---|---|---|---|---|---|
| 100k | 342,857 | 142 | 154 | 17.4 | 22.6 | 25.4 |
| 250k | 857,143 | 357 | 384 | 42.6 | 57.3 | 90.6 |
| 500k | 1,714,286 | 714 | 768 | 75.6 | 96.0 | 112.0 |
| 1M | 3,428,571 | 1,434 | 1,536 | 174.9 | 264.7 | 344.1 |

Two ceilings, **RAM binding before latency**: float32 vectors are 768 MB at 500k live, which
does not fit a 1 GB VPS beside the daemon and page cache (≈390k ceiling at ~600 MB available).
int8 quantization at 384 B/vector lifts that to ≈1.56M. Brute-force latency crosses 120 ms
between 500k and 1M live, interpolating to ≈600k.

## Outcome

**Single journal, with the live-only hot index as a requirement rather than an optimization.**
Both pre-committed gates passed at the nominal point.

Consequences recorded in ADR-003: group commit required; **ANN indexing and int8 quantization
are M0b requirements, not later optimizations**; brute force is acceptable only below ~250k
live memories.

## What this spike does not establish

- Real workloads may not resemble the statistical shape. The curve gives the forgetting policy a
  budget; it does not predict where a real user lands on it.
- I/O numbers are workstation-optimistic. The fsync calibration is published so they can be
  re-derived, but no VPS was measured.
- Retrieval *quality* is untouched here. This spike measures cost only. Quality is M0a/M0b.
